# 第 10 步：嵌套类型归位

## 1. 做了什么

上一轮源码树里，21,429 个嵌套类型（`<>c__DisplayClass`、`Array.ArrayEnumerator`、`List<T>.Enumerator`、
`ParticleSystem.LimitVelocityOverLifetimeModule` 这类）和顶层类型**平铺**在同一个命名空间里，
看不出谁属于谁。

这一步把它们的父子关系从元数据里解出来，源码树里改写成真正的 C# 嵌套类。

| 指标 | 之前 | 现在 |
|---|---:|---:|
| 嵌套类型归属 | 0 / 21,429 | **21,429 / 21,429** |
| 索引覆盖类型 | 57,487 | 57,487（零丢失） |
| 产物 | 467 个 `.cs` / 69 MB | 467 个 `.cs` / 76 MB |
| 生成耗时 | 5.8 s | 7 s |

嵌套深度分布：

| 层级 | 缩进 | 类型数 |
|---|---:|---:|
| 顶层 | 2 空格 | 36,051 |
| 一层 | 4 空格 | 21,080 |
| 二层 | 6 空格 | 328 |

467 个文件的 `{` / `}` 计数全部平衡。

## 2. 关键发现：数据一直都在，只是没去找

`extract_types_full.py` 的注释里早就写着：

```
+0x20  nestedTypesStart   (raw ^ 0x21FE571D - salt)，-1 = 无
+0x46  nested_type_count  u16 (raw ^ 0x7883) - (salt & 0xFFFF)
```

所以「每个父类型有 N 个嵌套类型、从第 S 个开始」这件事一直是知道的。
缺的只是**那段 `TypeDefinitionIndex` 数组本体在文件哪个位置**。

上一轮把它记成「元数据没有 nestedTypes 数组」，是误判。

## 3. 怎么定位数组的

### 3.1 先用已有字段自证

不急着找数组，先验证 `start` / `count` 自洽：

```
10390 个父类型，按 start 排序后逐个累加
→ 与每个父类型的 start 逐一吻合，零偏差
→ 累加末值 21,429 == sum(nestedCount)
```

**零空洞、零重叠、末值恰好等于总和**。这一步零成本，但把「数组是连续段」这个前提钉死了。

副产品：`nestedCount` 之和 21,429，而「namespace 为空的类型」有 22,186 个，差 757 ——
正是真正的顶层无命名空间类型（`<Module>` / `Locale` / `SR` / `<>f__AnonymousType0\`1`）。

### 3.2 用 ECMA 约束做判据

ECMA-335 规定：**嵌套类型 TypeDef 的 Namespace 字段必为空**。

所以数组里每个元素都必须是那 22,186 个之一。随机命中率 ≈ `(22186/57487)^21429`，实际为零。

```python
mv = memoryview(BUF)[:(FS//4)*4].cast("I")   # 56 MB 直接映射成 int 数组
for i in range(len(mv) - 21429):
    if not (mv[i] < NT and ok[mv[i]]):            # 预筛首元素
        continue
    if not (mv[i+21428] < NT and ok[mv[i+21428]]): # 预筛末元素
        continue
    if all(mv[j] < NT and ok[mv[j]] for j in range(i, i+21429)):
        hit(i)
```

**32 位窗口全库唯一命中一处：`metadata + 0x1C41FB0`**，扫 56 MB 用时约 30 秒。

> 16 位窗口会命中 21,431 个连续偏移，那是同一段数据在 16 位视角下的拆分解读
> （值都 < 57487，高 16 位恒为 0，而 0 号类型 `<Module>` 本身也合法）。
> **「16 位命中一大片」不是找到很多候选，只是 32 位结果的影子。**

## 5. 生成器改了什么

三处改动：

1. **`emit_type(ti, out, depth=0, spans=None)`** —— 缩进由 `depth` 决定
   （类型 `"  "*(depth+1)`，成员 `"  "*(depth+2)`），在类体末尾递归 emit 子类型。
2. **行号用 `try/finally` 记录** —— 类型有 `delegate` / `enum` 两个提前 `return` 分支，
   用 `finally` 保证每个类型都记上 `(start, end)`，否则索引会漏。
3. **索引改为全局收集** —— 这是必须的：嵌套类型 namespace 是空串，父类型 namespace 可能非空，
   两者**不在同一个 `.cs` 文件里**。按命名空间分组时子类型会被跳过（由父类递归输出），
   所以它的行号只能从「父类型所在文件」那边拿。

```python
g_spans = {}
for ns in sorted(groups):
    spans = {}
    for ti in tis:
        if ti in g.nest_parent:
            continue                  # 嵌套类型不单独占位
        g.emit_type(ti, out, 0, spans)
    for ti, (st, en) in spans.items():
        g_spans[ti] = (fn, st + 1, en - st)   # 嵌套类型也在 spans 里
```

**顺带的便利性质**：`entries` 按 `ti` 升序且 57,487 个类型全在，所以 `TYPES[i]` 恰好就是
类型索引 `i` 本身。前端拿 `parentIdx` 可以直接 `TYPES[parentIdx]` 取父类型，不用额外映射表。

## 6. 三个坑

### ① 十六进制抄错 6,848 字节，结果「看起来完全正常」

扫描输出十进制 `29630384`，手写成 `0x1C43A70`（正确是 `0x1C41FB0`），错位 1,712 个元素。

生成出来的东西居然还挺像样：父段累加校验 `bad=0`（这个检查只依赖 typedef 记录，不依赖数组）、
抽查也能看到 `<>c__DisplayClass` 之类的名字。

破绽在两处：**数组值域 `[1, 220544]` 超出 NT=57,487**，以及**重复子类型 671 个**。

> 凡是数组，一定要打印值域和唯一值个数。否则错位了也在静默通过。

### ② 环境里有 HTTP 代理，`curl 127.0.0.1` 会走代理

```bash
$ echo $http_proxy
http://127.0.0.1:52668
```

结果 `curl http://127.0.0.1:8765/api/index` 返回的是**代理缓存的旧响应**（6,265,266 B），
而磁盘文件已经是 6,603,974 B。排查了半天以为是服务端缓存。

```bash
curl --noproxy '*' http://127.0.0.1:8765/api/index
```

### ③ `serve_src.py` 的端口参数是 `--port`，不是位置参数

`serve_src.py 8765` 会被静默忽略、退回默认 8765 —— 恰好也是 8765，所以看起来「启动成功」，
实际参数没生效。要写 `serve_src.py --port 8765`。

## 7. 已知局限

- **嵌套类型在元数据里只有短名**（`Enumerator`，不带 `Parent.` 前缀）。源码树靠缩进表达归属；
  要拼全名做类型引用解析，需要沿 `nest_parent` 链上溯 —— `cs_type()` 目前没做，所以
  引用一个嵌套类型时可能只显示短名。
- **`parentIdx`（+0x00）与嵌套无关**。它是**基类**索引，值域到 351,793（超过 NT=57,487），
  说明是 `Il2CppTypeIndex`（含泛型实例化）而不是 `TypeDefinitionIndex`。别混用。
- **重复 token 7,637 个**。这是元数据本身的性质（各程序集 TypeDef token 从 `02000001` 各自编号），
  不是生成器 bug。要唯一定位类型只能用 `ti` 索引。
