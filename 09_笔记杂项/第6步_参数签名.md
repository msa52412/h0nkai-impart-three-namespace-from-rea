## 二、数据来源

| 信息 | 来源 |
|---|---|
| 返回类型 / 参数类型 / 参数名 / 是否 static | `bh3_methods_v2.tsv` |
| 方法 → RVA | `bh3_method_addr.tsv` 第 4 列 |
| 类型名 → typeIdx → 结构体 | `bh3_types_v5.txt` + `bh3_structs2.tsv` |

`flags` 是**十六进制**，`& 0x10` 就是 `MethodAttributes.Static`
（`ThrowHelper.IfNullAndNullsAreIllegalThenThrow` 的 `0093` → static；
`BulletinActivityConfig::.ctor` 的 `1886` → 非 static）。

## 三、最关键的设计：值类型必须拆成「按值」和「按指针」

MS x64 下：

- **≤8 字节的值类型** → 走寄存器，按值传
- **>8 字节的值类型** → 走隐藏指针

搞错这一点，从出错位置起**整串参数全部错位**。所以类型编码分两类：

| kind | 含义 |
|---|---|
| `p:<typeIdx>` | 指向结构体的指针（引用类型 / 数组 / 泛型 / **>8 字节值类型**） |
| `s:<typeIdx>` | **≤8 字节**的小值类型，按值传 |
| `i4 u4 u1 f4 …` | 定长标量，按真实宽度 |
| `p` | 无结构体的裸指针 |

返回类型同理：`Vector3`（12 字节）编成 `p:<idx>`，Ghidra 里显示 `Vector3 *` ——
这恰好就是隐藏返回缓冲区的语义，不会让 Ghidra 自己去摊平而错位 `this`。

## 四、两个解析坑

**1. 按 `", "` 切分会切坏泛型实参**

```
System.Converter`2<TInput,TOutput> converter
```

`<>` 里的逗号必须跳过 —— 用深度计数，只在 `depth == 0` 时断。

**2. kind 自身带冒号，必须按最后一个冒号切**

参数编码是 `p:6092:KOPNFGMFGBF`。按第一个冒号切得到
`kind="p"`、`name="6092:KOPNFGMFGBF"`，Ghidra 里就显示成
`pointer 6092:KOPNFGMFGBF`。改成 `lastIndexOf(':')` 才对。

## 六、顺带修掉的路径 bug

`gen_structs2.py` 的输出前缀从 `/bh3/` 改成 `/bh3v3/` 之后，
`ApplyTypes.java` 里的 `substring("/bh3".length())` 切出来是 `v3/UnityEngine`，
拼成 `/bh3v5v3/UnityEngine` —— 结构体全建到错误路径下。
脚本自身自洽所以没报错，但外部脚本按 `/bh3v5/...` 查一个都找不到
（表现为「结构体索引 0 个」）。

修法：前缀回到中性的 `/bh3/`，`ApplyTypes` 的 `ROOT2` 升到 `/bh3v6`。

## 七、还没做的

1. **调用点没跟着更新**：改了被调函数签名，Ghidra 不会自动回填所有 caller。
   需要在 Ghidra 里跑一次 Re-analyze（或重新反编译），caller 侧才显示实参类型。
2. **泛型实参没还原**：`List`1<uint>`、`T[]`、`T` 一律降级成指针。
3. **9,153 个方法**因声明类型没建出结构体而整行跳过，参数仍是 `param_N`。
4. 闭包类（`<>c__DisplayClass`）的 `this` 结构体没建出来时显示 `pointer this`。
