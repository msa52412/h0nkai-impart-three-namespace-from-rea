# 挑战面板 Task_3 / Task_4 指向迪拉克之海 —— 可行性结论

> 结论先行：**服务端改不了，必须改客户端本地配置（ctable.dat）**。
> 服务端能做的是把迪拉克页面本身跑通，这一部分已经可用。

---

## 1. 挑战面板卡片的真实身份

点击路径（来自 `PlayerLog`，非推测）：

```
WorldMapContainer/WorldMapUIManager_V2(Clone)/Canvas3D/MapPanel0/Challenge/Task_3/Cover
```

`MapPanel0` 下有三大分组，对应世界地图上方的页签：

| 分组 | 页签 | 代表节点 |
|---|---|---|
| `Attack` | 出击 | `Attack/OpenWorld/OpenWorldBtn`、`Attack/Regular_1/Cover`、`Attack/MainStory/MainStoryBtn` |
| `Challenge` | 挑战 | `Challenge/Task_1` … `Task_9`、`Challenge/EmptyFlag1` … `EmptyFlag4` |
| `Activity` | 活动 | `Activity/EventLab/Cover` |

`Challenge` 下是 **9 个固定槽位 `Task_1..Task_9`** 加 4 个空位占位符 `EmptyFlag1..4`。
槽位不是硬编码页面，而是**按配置顺序填充**的：有几个条目就点亮几个 Task，剩余显示 EmptyFlag。

## 2. 实测行为映射（服务端日志实证）

| 卡片 | 点击后进入 | 次数 |
|---|---|---|
| Task_3 | **什么都不开**（退出地图又重进，点击被吞） | 17 |
| Task_4 | `SinDemonExMainStubPageContext`（记忆战场） | 10 |
| Task_6 | `NewWantedMainPageContext`（悬赏委托） | 8 |
| Task_5 | 无 / 世界地图 | 3 |

Task_3 是**死卡**：客户端确有教程步骤指向它（`TutorialStepData` 里
`MapPanel0/Challenge/Task_3` 与 `Task_3/Cover` 都有引导），说明它原本是有效入口，
在 7.0 里目标玩法被关停后变成了空跳。

## 3. 槽位 ↔ 配置条目的对应关系

`WorldMap.json`（228 条入口）里存在一整组 `EntryID = 1001..1012` 的入口，
图片路径正是 `SpriteOutput/WorldMap/Entry/OWTask_1` 这类：

| EntryID | ID | FeatureType | 图片 | 说明 |
|---|---|---|---|---|
| 1001 | 1 | 7 | `Entry/OWTask_1` | 开放世界任务 |
| 1003 | 3 | 2 | `Entry/Extra_1` | 外传（**点击无效**） |
| 1004 | 4 | 8 | `Entry/MutilTask_1` | 多模式任务（内容为 ExBoss 关卡 42000001…）→ **记忆战场** |
| 1006 | 6 | 114 | `newbie37/entrance_truecolor` | → **悬赏委托** |
| 1009 | 9 | 9 | `Entry/Regular_1_100` | 主线普通关 |
| **1012** | 15 | **108** | **`OWEndless/Cover_11`** | **迪拉克之海（无尽）** |

Task_4 → 1004、Task_6 → 1006 完全对上实测行为，因此
**`Task_N` = 第 N 个 Challenge 分组条目 = `EntryID 100N`**。

迪拉克是 `EntryID 1012`，排在**第 12 位**，而槽位只有 9 个 → 它永远不会被点亮。
这就是「挑战面板里看不到迪拉克」的根因。

## 4. 为什么改不了服务端

`WorldMapData` 协议（`GetWorldMapDataReq/Rsp`）只携带每张世界地图的
`world_map_id / begin_time / end_time / weight / advance_time`，**不含入口列表**。
入口的 `EntryID`、`FeatureType`、显示分组全部由客户端本地 `WorldMap.json` 决定，
而该表打包在 `BH3_Data/StreamingAssets/ctable.dat` 里（28,160,000 字节，整段熵 7.993，全密文）。

服务端仓库 `run/Resources/ExcelOutputAsset/*.json` 是同一批表的**解密副本**（1658 张），
可读但改它不影响客户端。

另外验证过：世界地图 UI 预制体
`0a95a3510bffb1a31fdef2cae36e8783.wmv` 的 body@21042663（SF 412587 字节）
里**不存在** `1001..1009` 这样的入口 ID 数组，也没有连续 ID 序列 ——
说明绑定关系是运行时按配置生成的，不是预制体序列化字段。

**当前可用的入口：世界地图 → 出击页签 → 开放世界按钮。**

## 6. 两条可选路线

### A. 解 ctable.dat（唯一能真正改卡片的路线）

需要：定位 ctable 加载器 → 提取密钥/算法 → 实现解密 → 改 `WorldMap.json`
里 `EntryID 1003`（或 1004）的 `FeatureType` 为 `108` → 重新加密 → 替换。

- 难点：`UserAssembly.dll`（190MB）里**搜不到明文 `ctable.dat`**，字符串被混淆，
  必须靠 Ghidra 交叉引用定位；`ctable` 的 5 处字节命中全是 `Selectable`/`Rejectable`/`collectable` 的巧合。
- 收益：一旦打通，所有配置表可改 —— 人物、关卡、玩法全解锁，也是后续「加人物模型」的前置。

### B. 不碰配置，改用已存在的出击页入口

零成本、已验证可用，但不是用户要的「挑战面板卡片」。

## 7.6 ctable.dat 加载器已定位（关键进展）

`ctable.dat` 的加载器**不在 UserAssembly.dll，而在 `UnityPlayer.dll`**（魔改过的 Unity 运行时）。

| 项目 | 地址 / 结论 |
|---|---|
| 字符串 `"ctable.dat"` | VA `0x1815897C0`（file 0x15887C0，`.rdata`） |
| **唯一代码引用** | VA `0x180D55935`（`lea rdx,[rip+0x833e84]`） |
| 加载器函数 | 起于 `0x180D558E0`，出参缓冲初值 `0x400`，全局 `0x1817990D0/0x1817990E0` 是 MSVC vector 的 begin/end |
| **解密调用** | `0x180D559D0  call 0x1800E0070`（失败串 `"HandleCheckCmd failed: %d"`） |
| 解密函数 | `0x1800E0070`，**控制流平坦化**（`jmp rax` + 跳表 @ `0x1816F1660`） |
| 相邻提示串 | `"[miHoYo] GetDecryptVectorEx error %d"` |

密文特征（实测）：

- 28,160,000 B，**是 16 的整数倍**（1,760,000 块）
- 16 字节块 **零重复**，32 字节块零重复 → 不是 ECB，是链式或流式
- 全段熵 7.993，头尾一致 → 无明文头，整文件加密
- 明文 `ExcelOutputAsset` 共 394.55 MB，密文只有 26.86 MB
  → **先压缩再加密**（解密后还要解压，算法待定，可能是 zstd/lz4）

### 不需要密钥的破解思路（重点）

若最外层是流密码或 CTR：

```
密文[i] = 明文[i] XOR 密钥流[i]
```

密钥流与明文无关，所以只要拿到**一次解密后的明文**，就能算出密钥流；
之后任意改写明文都能原地重加密，**完全不需要密钥**。
（只有 CBC 才需要密钥，届时需再从内存里搜 AES-256 密钥表。）

实现已就绪：`ctable_crack.py`（`check` / `keystream` / `encrypt` 三个子命令），
配合 `memdump.py` 从运行中的进程里抓明文。
