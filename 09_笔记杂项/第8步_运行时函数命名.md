# 第 8 步交付：il2cpp 运行时热点函数命名

> 目标：让反编译里 `FUN_1804fe400()` 这类调用变成有语义的名字
> 结果：**13 个符号，把「调用未命名函数」的占比从 59.6% 压到 17.4%**

---

## 1. 成果

| 指标 | 命名前 | 命名后 | 变化 |
|---|---|---|---|
| 指向**已具名**函数的调用边 | 1,768,357（40.4%） | **3,610,737（82.6%）** | +1,842,380 |
| 指向**仍是 `FUN_`** 函数的调用边 | 2,605,085（59.6%） | **762,705（17.4%）** | −1,842,380 |
| 全库有 C# 名的函数 | 332,965（75.15%） | 332,980（75.15%） | +15 |
| 全库仍是 `FUN_` 的函数 | 110,104 | 110,089 | −15 |

函数数只加了 15 个，调用边搬走了 184 万条——因为命中的全是**每个 C# 方法都会踩**的入口。

## 3. 判据：为什么敢这么命名

### 3.1 字符串常量做地面真值

这几个函数有固定形态：

```asm
180448976  MOV RCX,[0x1899db1c0]      ; corlib（Il2CppImage* 全局）
18044897d  LEA R8,[0x1881a1f38]       ; name
180448984  LEA RDX,[0x1881a1de8]      ; namespaze
18044898b  CALL 0x18042d650           ; Class::FromName(image, ns, name)
180448993  CALL 0x1804457f0           ; Object::New(klass)
1804489aa  CALL 0x180447cf0           ; Raise
1804489c5  INT3
```

两个 `LEA` 指向 .rdata 的 C 字符串，直接读出来：

| 地址 | 内容 |
|---|---|
| `0x1881A1DE8` | `"System"` |
| `0x1881A1F18` | `"IndexOutOfRangeException"` |
| `0x1881A1F38` | `"NullReferenceException"` |
| `0x1881A2080` | `"ArrayTypeMismatchException"` |

所以「哪个函数抛哪个异常」是**读出来的**，不是猜的。

### 3.2 调用点上下文闭环

```c
/* IsPatched：对象空判断 → 抛空引用 */
if (**(longlong **)(klass + 0x28) == 0) {
    FUN_1804fe400();
}
/* IsPatched：数组越界判断失败 → 造并抛 IndexOutOfRangeException */
if ((uint)id < *(uint *)(arr + 0x18)) { return ...; }
uVar4 = thunk_FUN_180436120();
FUN_1804fe3d0(uVar4, 0);
```

### 3.3 汇编形态

- **noreturn 桩** = `SUB RSP,0x28; CALL X; INT3`（10 字节）
- **thunk** = 5 字节 `E9 xx xx xx xx`
- `0x1804FE040–0x1804FE4A0` 整片是 MSVC 增量链接的 jump thunk 表，同表还混着
  `CoTaskMemAlloc`、`K32GetProcessImageFileNameW`、`inet_ntop`、`_guard_check_icall` 等导入桩

## 5. 踩到的三个坑

1. **本地 `UserAssembly_slim.dll` ≠ Ghidra 里的 `UserAssembly_fixed.dll`**
   slim 是被 TenProtect 处理过的落盘文件（两个 `.reloc`、`.tvm0`、`edata2`），
   按 VA 读字节读到的是 Boehm GC 的字符串。**所有按 VA 读字节的操作必须在 Ghidra 里做。**

2. **PE 节表漏读 `SizeOfOptionalHeader`**
   节表起点是 `e_lfanew + 4 + 20 + 0xF0`，我硬编码成 `+24`，整体错位 240 字节。
   离谱的是 `.text` / `.rdata` 的 RVA 碰巧还对——**错得很像对的**，最难发现。

3. **Ghidra 会自动把 thunk 改名成 `thunk_<目标新名>`**
   目标函数改名后，thunk 名字被同步，于是 `ApplySymbols.java`（只改 `FUN_` 开头）
   把两个桩判成 `KEPT` 跳过。新写 `ApplyRt.java`：强制改名 + 支持 `setNoReturn`。

## 6. 还没做的

| VA | 入度 | 形态 | 为什么没命名 |
|---|---:|---|---|
| `0x18043E4C0` | 103,744 | 锁 → 调 `0x18043E550` → 失败带类名抛异常 → 返回 1 | 疑似 `Class::Init` 另一入口，标志位对不上 |
| `0x1803EE250` | 66,537 | thunk → `0x18042CF20`，含 `memcpy(..., slot-0x10)` | 疑似泛型虚方法适配器 |
| `0x1804FE260` | 51,733 | thunk → `0x180436090` = `idx==-1 ? 0 : table[idx]` | 疑似元数据 usage 表查询 |
| `0x1804FE040` | 44,931 | thunk → `0x180442320`（接口/类型匹配） | 语义未定 |
| `0x1804FE070` | 36,024 | 用类名拼消息后抛 | 疑似 `RaiseTypeInitializationException` |
| `0x1804FE0E0` | 22,559 | 5 字节 `JMP 0x180445770` | **曾疑为 `unbox`，dump 汇编后否定**：目标是 `strlen` + 构造 std::string 的字符串哈希 |

**判据纪律**：只收三类硬证据能闭环的。`0x1804FE0E0` 就是反例——形态上极像
`il2cpp_codegen_unbox`（返回 `obj+0x10`），真去 dump 才发现是字符串哈希。
**错名比 `FUN_` 更有害**，因为它会让后续所有推理建立在错误前提上。
