## 三、过程中查出的布局错误（已修）

写回成功后，发现 `min_player_level`（`uint`，4 字节）被写进了 8 字节字符串指针：

```c
*(undefined **)&this->min_player_level = _DAT_189b4a238;   /* ← 类型宽度对不上 */
```

用构造函数做地面真值逐条核对，确认 **22 个字段全是实例字段、零 static**，
上一轮把 `end_time` / `bulletin_id` / `max_player_level` 误判成 static 了。

根因：编译器会合并写 `mov qword ptr [rax+0x18], 0` 一次清零两个 4 字节字段，
扫描器只记访问基址 `0x18`，`end_time`(0x1C) 永远不出现在观测里 → 被判 static
→ 其后所有字段名整体前移。

`/bh3/proto` 下被误标 static 的字段比例：**44.5%**（5,834 / 13,103）→ 真实接近 0。

改成「声明顺序 + 自然对齐」纯打包后，逐条吻合：

| 偏移 | 宽度 | 构造函数写什么 | 对应字段 |
|---|---|---|---|
| 0x10 | 8 | 0 | activity_id + activity_type |
| 0x18 | 8 | 0 | begin_time + **end_time** |
| 0x20 | 4 | 0 | **bulletin_id** |
| 0x28 | 8 | new List | mission_ids |
| 0x30 | 8 | new List | type_param_list |
| 0x38 | 8 | string.Empty | type_param_str |
| 0x40 | 8 | 0 | min_player_level + max_player_level |
| 0x48 | 8 | new List | item_list |
| 0x50–0x70 | 8×5 | string.Empty | title_name … description |
| 0x78 | 4 | 0 | weight |
| 0x80, 0x88 | 8×2 | string.Empty | background_path / text_image_path |
| 0x90 | 8 | new List | currency_list |
| 0x98 | 8 | string.Empty | unlock_param_str |
| 0xA0 | — | 未写 | extensionObject |

实例尺寸 168 字节。
